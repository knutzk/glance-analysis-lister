# Provenance

[Documentation index](README.md)

Generated files record which registry, configuration and generator produced
them. This helps distinguish source-data changes from changes in curation or
rendering.

## Reproducible output

The same snapshot bytes and basename, effective profile, generator contents and
revision, and runtime produce byte-identical pages, assets and reports. Tests
cover separate processes, Python hash seeds, time zones and output locations.

Unchanged files are not rewritten, preserving timestamps and inodes. Missing or
modified generated files are replaced; unrelated files remain untouched. The
log reports written/unchanged counts. These counts are excluded from the report
because they depend on the existing output directory.

## Generated headers

Markdown comments record the generator Git commit, registry filename and SHA-256,
and hashes of the effective profile and generator contents. YAML front matter
stays first. Copied CSS and JavaScript record the source commit and retain their
SPDX notices; those assets are independent of the registry.

A modified checkout is marked `-dirty`. Source archives and wheels retain the
revision recorded at build time; unavailable revisions are labelled `unknown`.
No generation timestamp is added. These notices do not apply the package licence
to registry content.

## Profile and generator hashes

The report's `profile` contains the group, display title and selected publication
policy. Its canonical `profile_sha256` excludes unrelated TOML groups, comments
and formatting.

`generator.content_sha256` hashes package Python files and browser assets by
relative name and content. It distinguishes local edits even when both builds
have the same `-dirty` commit label. Installed packages and checkouts with
identical contents have the same content hash.

Citation and identifier data are covered by the snapshot hash and its
[curation provenance](registry.md); rendering does not reload those dictionaries.
Registry construction records identifier evidence, dictionary hashes and build
metadata.

## Example: which changes affect the result?

Suppose you render the same DEMO snapshot twice, then edit the publication policy:

| Change | Expected result |
| --- | --- |
| Render again with identical inputs, configuration and generator | Generated bytes and file timestamps remain unchanged. |
| Add a comment to the policy TOML | The effective profile hash stays the same. |
| Edit an unrelated group's policy | The DEMO profile hash stays the same. |
| Change the DEMO publication title | The profile hash changes, along with the publication headings. |
| Change a record in the snapshot | The snapshot hash changes, even if that field is not displayed. |

Use these hashes to identify which input changed before comparing the rendered
text. A different hash records a difference; it does not by itself indicate an
error.
